# Bundled BK7258 packaging inputs

These files let `tools/package_bk7258_bundled.py` build a complete L2-dev
`all-app.bin` without the Armino SDK or a `beken_genie` build tree, so a
developer who only has this repository plus an OpenVela workspace can compile,
package and flash a CPU0 image.

Their SHA-256 values are locked in
[`../profiles/bk7258-devkit-l0-bundled.json`](../profiles/bk7258-devkit-l0-bundled.json)
and checked by `tests/test_bk7258_bundled_packaging.py`.

## Contents and origin

| File | Bytes | Origin | Form |
| --- | --- | --- | --- |
| `normal-bootloader.bin` | 52352 | Armino SDK (`bk_avdk_smp`), branch `release/v3.1.1`, revision `d2ded037798530175e5dc5cde6fa1878f5d5ef35`, path `cp/components/bk_libs/bk7258/bootloader/normal_bootloader/bootloader.bin` | Vendor prebuilt binary, redistributed unmodified |
| `bk_ota_partitions.json` | 803 | `beken_genie` BK7258 build tree, `partitions/bk_ota_partitions.json` | Vendor partition description, redistributed unmodified |
| `ap-placeholder.bin` | 66 | Generated by [`../../tools/make_ap_placeholder.py`](../../tools/make_ap_placeholder.py) | Synthetic; contains no vendor code |

`normal-bootloader.bin` is padded and combined with the 256-byte serialized
partition table at package time, which reproduces the vendor staged Bootloader
`d27be983a1c0eb80033e4ad8877aa16c6df87c55e96c7dae238a3a6866abb4a0` exactly. The
bundled image therefore carries a byte-identical Bootloader partition to the
vendor-profile image.

## Licensing note

Both vendor source trees carry an Apache-2.0 `LICENSE` at their root. Two caveats
worth recording rather than assuming away:

- The Armino SDK checkout has no `NOTICE` file, so the attribution Apache-2.0
  §4(d) would normally propagate is not available from the source tree.
- Prebuilt binaries inside a vendor SDK sometimes carry terms separate from the
  repository-root license. `normal-bootloader.bin` is such a prebuilt blob.

Bundling these two vendor files is a deliberate team decision, taken so that the
build/package/flash path is reproducible from this repository alone. Re-check it
if Beken publishes different terms for the prebuilt Bootloader, and do not extend
the same reasoning to other vendor artifacts by default. The vendor AP payload is
specifically **not** bundled: it statically links third-party commercial
components, which is why this profile uses a synthetic placeholder instead.

## The AP placeholder is not a working AP

The L0 contract keeps the secondary cores unreleased, so the AP partition only
has to be occupied by a well-formed payload. The placeholder is a 16-word vector
table whose reset handler and exception vectors all branch to one self-branch
loop at `0x02160041`, so a hypothetical Bootloader handoff parks the core instead
of executing `0xff` padding.

On 2026-08-12 a bundled image
(`675ae968801e440ff7a2eb936d54acadf1117fc852ec050bf72fac6f38759d56`) was flashed
to a DevKit and the CPU0 console came up. So the placeholder is no longer
speculative: the vendor Bootloader does boot CP with a 66-byte AP partition. The
loader reported `Last 4K CRC_Verify ->pass`, `WriteFlash ->pass` and
`Writing Flash OK`; the console result is operator-reported, because no UART log
was captured for that run.

What this still does not establish:

- whether the vendor Bootloader inspects or validates the AP partition at all,
  as opposed to simply never releasing the secondary cores;
- AP release, peripherals, networking, USB or sustained operation.

Keep the vendor recovery image
(`1613a6018553de9ebb0564572b090844253688af53c9bcc3de7c5b40f06db89d`) available,
and capture a UART log on the next run so the console result is recorded.

When an OpenVela AP component exists, add a profile for it rather than replacing
this placeholder: the container encoder, bundled Bootloader and partition layout
are all AP-agnostic, and the placeholder already uses the AP XIP vector base
(`0x02160000`) a real AP component would link against.
